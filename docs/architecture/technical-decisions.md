# 技术选型与兼容决策 · 待评审

> 文档性质：设计/边界文档：可能含早期目标与原型现状，是否已实现须查当前状态。 [当前状态](<../status/current-status.md>) · [知识库入口](<../README.md>)

此文不是“选最先进版本”的清单。优质依赖需满足维护活跃、许可适配、安全修补可用、类型/生态成熟、可替换，以及实测成本可接受。

| 决策 | 推荐 | 替代与代价 | 升级/退出条件 |
|---|---|---|---|
| 语言/结构 | TypeScript模块化单体，前后端共享契约 | Go后端吞吐/工具链优秀，但初期两套语言与DTO维护增加成本 | 实测瓶颈或团队能力支持时只替换独立worker，不全盘重写 |
| Web | React + Vite，固定shell+少量命名槽 | Next适合SSR/公开SEO，但初期私人工作台不需完整SSR平台 | 公开知识站有SEO需求时增加只读发布层 |
| HTTP | Fastify + Zod，显式路由/服务 | 自动RPC可降样板但加框架耦合；Nest增加初期结构量 | DTO增多后引入OpenAPI契约生成，不同时维护两套schema |
| 数据库 | SQLite用于开发/单实例；设计SQL关系边界 | PostgreSQL适合多人生产/并发，增加部署成本 | 发布形态确认后定首个生产数据库，所有迁移与仓储测试针对它执行 |
| DB访问 | 有序SQL迁移+小仓储；评估Drizzle而非立即引入 | ORM带类型与迁移工具，但不自动解决租户scope/CAS | 关系表与查询稳定后做小规模试用，避免每层都套Repository接口 |
| 编辑器 | M1先保留textarea；复杂编辑需求再评估CodeMirror6 | TipTap/Lexical适合结构化富文本，但Markdown往返与插件schema更复杂 | 用户明确需要富编辑再选一种，不同时维护两套文档真相 |
| Markdown | marked + sanitize-html，安全策略在宿主 | unified/remark适合AST/wikilink插件但迁移要跑渲染金样本 | 实现wiki链接/AST转换时评估，不能仅为生态热度替换 |
| 测试 | node:test负责单元/API；Playwright负责浏览器闭环 | Vitest便于前端单元，但增加第二执行器 | 复杂UI出现后按收益引入；先保证端到端关键路径 |
| 身份 | 首期账号/会话方案需独立ADR；推荐评估成熟认证库及OIDC适配 | 自建密码方案可控但承担重置、验证、封禁、会话安全长期责任 | 设计确认前不把实验scrypt模块当正式认证选型 |
| 组件 | schema约束声明式block + React受信renderer | 任意React/JS灵活但无法靠声明权限隔离 | 高级代码扩展另立安全项目，不隐藏在市场功能里 |
| 检索 | 首期中文关键词方案明确能力边界，评估FTS5/tokenizer | PostgreSQL全文/pgvector及专门搜索服务各有运维成本 | 固定中英文评测集证明召回不足时再加向量，不为AI标签先建集群 |
| 模型 | 一个OpenAI-compatible适配器 + 宿主broker | 多厂商SDK覆盖多但扩大兼容与安全面 | 第二个真实provider需求出现后泛化；endpoint自定义必须受控 |
| 队列 | DB任务表+单进程worker，幂等/恢复先行 | Redis队列便于多worker但多运维组件 | 单机吞吐或隔离需求有测量证据后采用 |
| 文件 | 授权下载+内容寻址本地存储 | S3兼容存储适合容量/多实例 | 单实例容量与部署形态需要时增加适配器 |

## 三种版本不要混用

1. 宿主插件API版本：决定契约是否可加载。
2. 发布包/组件release版本：固定不可变内容，用户明确升级。
3. 数据schema/config版本：决定迁移，迁移失败不覆盖旧数据。

HTTP破坏性变化需明确版本与迁移窗口；M0尚未稳定API可调整，但要写变更记录并更新客户端/测试。锁文件纳入Git；依赖major升级单独验证，安全审计通过不等于无风险。

## 需要单独批准的ADR

- ADR-001：自托管/托管优先与生产数据库。
- ADR-002：身份提供方与管理员初始化、账号恢复策略。
- ADR-003：用户组件能力范围与第三方代码是否进入首发。
- ADR-004：页面数据模型、Markdown往返、富编辑器选择。
- ADR-005：模型凭据托管与出站网络策略。

每份ADR只记录问题、备选、选择、理由、代价、可逆性与验证方法。没有真实决策不新建空模板文件。
